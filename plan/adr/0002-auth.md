# ADR 0002: Sign-in and token storage

> **Status:** accepted · 2026-10-17

## Decision
- OAuth 2.0 authorization code flow with PKCE against Entra ID v2 endpoints, as a **public
  client**, implemented directly on `reqwest` (PKCE, form bodies; the flow is small enough that the `oauth2` crate added nothing). The system browser handles the interactive step; a
  loopback listener on `127.0.0.1:<ephemeral>` receives the code (RFC 8252). `state` checked,
  `nonce` checked against the ID token.
- Scope `https://graph.microsoft.com/.default offline_access openid profile` (tenant-wide admin
  consent makes `.default` return the consented list).
- Refresh token stored in the OS credential store via `keyring` (macOS Keychain, Windows
  Credential Manager, Secret Service on Linux). Access tokens kept only in memory.
- Claims challenges and `interaction_required` pause sync and prompt re-sign-in.

## Alternatives
| Option | Why not |
|---|---|
| MSAL | No official Rust MSAL; wrapping MSAL for C++/ObjC means FFI and `unsafe` |
| Embedded webview sign-in | Breaks the macOS Enterprise SSO extension, passkeys and some Conditional Access policies; phishing-shaped UX |
| Device code flow | Fine for `quorum-cli login --device` as a fallback, not for the desktop UX (and often blocked by CA policy) |
| `azure_identity` | Aimed at service credentials; its interactive flows are thin and it pulls a large dependency tree |

## Consequences
- If the tenant requires a brokered, device-bound token (rare), we will need the Microsoft
  Enterprise SSO plug-in path to be enough; checked in M1 against the real tenant.
